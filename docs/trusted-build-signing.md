# Trusted builds and binary signing

Design of record for signing cloudfra release binaries in CI and verifying
them at install time. It replaces the trust model drafted in
[cloudfra/gh-runner#25](https://github.com/cloudfra/gh-runner/issues/25) and
resolves the sixteen findings posted in
[the review comment](https://github.com/cloudfra/gh-runner/issues/25#issuecomment-7017025136).
Implementation issues:
[#27](https://github.com/cloudfra/gh-runner/issues/27) ceremony,
[#28](https://github.com/cloudfra/gh-runner/issues/28) signer service,
[#29](https://github.com/cloudfra/gh-runner/issues/29) revocation and rotation.

## 1. What is broken today

The release recipe signs bytes that are never shipped. In
`Makefile_build.mk`, the `build/release/%` recipe signs the linked ELF with
OpenSSL CMS, then `objcopy --add-section .cloudfra_signature=…` rewrites the
same file. Verified on a real `certtool` asset:

```console
$ openssl cms -verify -inform DER -in pre.objcopy.sig -content pre.objcopy \
    -noverify -binary
signature verification successful
$ openssl cms -verify -inform DER -in pre.objcopy.sig -content shipped \
    -noverify -binary
verification failed: 4 bytes read, SMIME_read_CMS: no content PKCS#7 header
```

`shipped` is the asset published on every release. So `objcopy` is the only
verifier in production, it checks only that the section exists, and the
signature never covers the published bytes. The section also changes the
hash and moves `e_shoff`, so post-embed verification is impossible: a
self-hash is a fixed point. Two further facts make the embed worthless today:
the private key is missing from every release bundle, and `openssl` has no
flag in `cms` or `smime` that verifies an embedded PKCS#7 section.

Consequences for the design below: the ELF section is deleted, and the
release manifest becomes the only carrier of trust.

Three more defects worth naming here because they change the design, not
just the wording:

- Nothing in the pipeline is timestamped. `openssl` cannot add a RFC 3161
  `signedAttrs` attribute to a CMS signature (`openssl cms -help` lists no
  timestamp option, and `openssl smime -help` has only `-verify`, never
  `-sign`). Combined with a ≤ 90-day leaf and "reject an expired signing
  certificate", every signature self-destructs in under three months.
- The current signing certificate is self-issued: the Makefile builds a
  throwaway root and leaf whenever `certs/localhost/signing/{leaf,key}.pem`
  are absent.
- `linux_arm64` and `darwin_arm64` assets are unsigned, about 40% of the
  fleet.

## 2. Scope

In scope:

- Signing every release asset of every template-go consumer, on all five
  platforms.
- A verifier library used by the production and development updater tracks.
- Key ceremony, lifetime policy, revocation, rotation, anti-rollback.
- The `gh-runner` fleet prerequisites: firewall egress, a protected
  admin lane, artifact-only deployment.

Out of scope, stated so nobody is surprised later:

- Windows SmartScreen reputation and macOS notarization. A private root
  gives none. The Authenticode signature is useful to *our* verifier, not to
  a default Windows install. Buying reputation means a public CA or an
  EV Authenticode certificate, which is a separate decision.
- Replacing Windows Authenticode.
- Multi-party threshold signing. The Phase 2 hardening step (§11) moves the
  production CA key onto a second non-exportable YubiKey, which is the
  closest step to that.

## 3. Trust model

| Element           | Decision                                                                                                                                                                              | Why                                                                                                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Root CA           | ECDSA P-384, 10 years, `--max-path-len 1`, YubiKey 5 PIV slot 9c, touch always. Generated by `certtool --yubikey-generate-root`.                                                      | The only long-lived secret. Never signs a manifest or a CRL.                                                                                                                            |
| Production CA     | ECDSA P-384, 365 days, `--max-path-len 0`, `KeyUsage = certSign \| crlSign`, EKU `codeSigning`. Issued by the root with `certtool --yubikey`, private key held by the signer service. | Ceremony is once a year, not per release. `crlSign` is mandatory: Go's `x509.CreateRevocationList` states "the crlSign bit must be set in KeyUsage in order to use it as a CRL issuer". |
| Development CA    | Same shape, 365 days.                                                                                                                                                                 | A leaked dev key must not be able to sign a production manifest.                                                                                                                        |
| Leaf certificates | Issued by the CA **by the signer service itself** on demand, ≤ 90 days production, ≤ 14 days development.                                                                             | No ceremony per release; the signer already holds the CA key. Short leaves keep blast radius small.                                                                                     |
| Trust anchor      | Pinned CA **SPKI** hashes, compiled into each consumer app from `updater/anchors.json`.                                                                                               | Pinning the CA rather than the leaf is what makes short leaves survivable.                                                                                                              |
| Trust carrier     | `manifest.json` + `manifest.sig` release assets. No ELF section, no sidecar per binary.                                                                                               | One signature per release covers all platforms, and the signed bytes are the shipped bytes.                                                                                             |
| Timestamping      | RFC 3161 on Windows Authenticode only, added by `osslsigncode -ts`. Manifest signatures carry no timestamp; see §9.                                                                   | `osslsigncode` supports it ("Authenticode timestamping with `-t`", "RFC 3161 timestamping with `-ts`"); OpenSSL CMS does not.                                                           |
| Revocation        | CRLs, generated in Go, published as files in a public repo. No OCSP.                                                                                                                  | Go stdlib has `x509.CreateRevocationList` / `ParseRevocationList` and no CMS parser, so CRLs are the one revocation path we can implement with no new dependency.                       |
| Rollback          | Monotonic `seq` assigned by the signer, stored by the verifier.                                                                                                                       | The old design never said what to do with an old-but-valid manifest.                                                                                                                    |

## 4. Invariants

Every implementation step must preserve these.

1. A signature covers the exact bytes of the published asset. Nothing
   mutates a signed file, and nothing is signed before its last mutation.
2. Every release has exactly one `manifest.json`, and every published asset
   appears in it with SHA-256 and size.
3. `seq` for a given `(repo, app, track)` increases by one per signature
   request and is never reused or decreased.
4. No signing key is reachable from a runner. Runners hold no signing
   capability of any kind, and the only network path to the signer is from
   the runner subnet.
5. The verifier never executes a downloaded binary before every check in
   §8 passes.
6. A private YubiKey root key is never overwritten after an intermediate
   exists: `certtool --yubikey-overwrite` documents that "The old key is
   destroyed", which makes already-issued intermediates unrevocable and
   their chains unresolvable.
7. A CA issues nothing below its intermediates: `--max-path-len 0` on both
   CAs, so a leaf cannot mint a CA.
8. The self-signed fallback (`make` generating a throwaway root and leaf
   when `certs/localhost/signing/` is missing) is deleted last, after the
   signer path is proven, and its removal is measured first: nine consumers
   × fourteen apps × five platforms is the blast radius.

## 5. On-disk contract

Release assets, added to what `create-release.yaml` already uploads:

| Asset              | Contents                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------- |
| `<app>-<platform>` | unchanged names; Windows assets are Authenticode-signed                                                        |
| `manifest.json`    | exact bytes returned by the signer, published verbatim                                                         |
| `manifest.sig`     | base64 of the DER ECDSA P-384 signature over SHA-384 of those bytes                                            |
| `sha256sums.txt`   | kept for existing tooling such as `DownloadVerified()` in `gh-runner`; informational only, never a trust input |

`manifest.json`, one line, keys in this order, UTF-8, no trailing newline:

```json
{"schema":1,"app":"gowebserver","repo":"cloudfra/gowebserver","track":"production","version":"v3.8.2","commit_sha":"0f2b1c…","run_id":19884477123,"seq":41,"published_at":"2026-11-19T18:04:11Z","leaf_serial":"3fa9c2…","files":[{"name":"gowebserver-linux_amd64","platform":"linux_amd64","sha256":"c3d1…","size":74393488,"authenticode":false}]}
```

Signing and verification use the Go stdlib only:

```go
sig, err := ecdsa.SignASN1(rand.Reader, key, sha512.Sum384(manifestBytes)[:])
ok := ecdsa.VerifyASN1(leaf.PublicKey.(*ecdsa.PublicKey), sha512.Sum384(manifestBytes)[:], sig)
```

`manifest.sig` holds `base64.StdEncoding.EncodeToString(sig)`. CI must
publish the manifest bytes returned by the signer byte-for-byte; re-encoding
JSON anywhere in the pipeline invalidates the signature.

## 6. Signer service

Lands in `cloudfra/gh-runner` as a new deployment (`signer/`), per
[#28](https://github.com/cloudfra/gh-runner/issues/28). A single static Go
binary on its own node in the existing Terraform tree, holding the two CA
keys and certs.

| Method | Path           | Purpose                                                                                                                                                                                        |
| ------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/v1/manifest` | Input: `app`, `track`, `version`, `commit_sha`, `run_id`, `files[]`. The signer assigns `seq` and `published_at`, mints or reuses a leaf, returns the final manifest bytes plus the signature. |
| `POST` | `/v1/pe`       | Input: unsigned PE. Runs `osslsigncode sign -certs … -key … -ts … -in … -out …` and returns the signed PE.                                                                                     |
| `POST` | `/v1/crl`      | Returns a DER CRL for one track, from a queued revocation list.                                                                                                                                |
| `POST` | `/v1/revoke`   | Adds a leaf serial to the queue. Operator-only, see below.                                                                                                                                     |
| `GET`  | `/healthz`     | Unauthenticated liveness; returns nothing about keys.                                                                                                                                          |

Design rules:

- There is **no** `sign(digest)` verb. A digest-only API cannot serve
  Authenticode, which signs a PE structure rather than a hash, and
  `osslsigncode` has no remote-PKCS#11 client. The signer performs the
  operation, not the primitive.
- Requests are authenticated with the GitHub OIDC id-token, validated
  against `https://token.actions.githubusercontent.com` using the published
  JWKS (discovered at
  `https://token.actions.githubusercontent.com/.well-known/openid-configuration`).
  Checks: `iss` exact, `aud` is the org, `nbf`/`exp`, and the exact
  allowlist `repository`, `repository_owner`, `ref_type`, `ref`,
  `event_name`, `job_workflow_ref`, `environment`.
  The `environment` claim only appears when the job declares
  `environment:`, which is also what makes GitHub evaluate the environment's
  protection rules: "Each job in a workflow can reference a single
  environment. Any protection rules configured for the environment must pass
  before a job referencing the environment is sent to a runner."
  Compare `repository_id` alongside `repository` — GitHub notes that
  repositories created after July 15, 2026 use "an immutable default subject
  format" containing owner and repository IDs, so `sub` is not stable across
  renames for older repos.
- mTLS was the earlier plan and is dropped: it would make this service a
  certificate authority for runners, which is a second PKI nobody asked for.
  Transport security is the pinned OIDC issuer TLS chain; the network
  boundary is a firewall rule allowing inbound 443 only from the runner
  subnet. The one egress exception the signer node needs is the OIDC issuer
  for JWKS.
- The signer needs outbound access to one RFC 3161 TSA for `-ts`. Pick the
  TSA in the same PR that turns on PE signing; a TSA outage fails the
  publish step, which is intended.
- `seq` state lives in `/var/lib/ghsigner/seq/<repo>_<app>_<track>`. The
  counter is incremented and fsynced **before** signing, so a crash burns a
  number rather than reusing one.
- CA keys on disk: Phase 1 keeps them as `0600` files, encrypted at rest
  with `age`, unwrapped at start by an operator present at the console.
  Phase 2 (§11) moves them to a second YubiKey PIV slot; `osslsigncode`
  supports `-pkcs11module` and `-pkcs11cert` per its synopsis
  (`[-certs file | -spc file | -pkcs12 file]` plus PKCS#11 options), so the
  PE path can go non-exportable without a format change.
- `/v1/revoke` is not callable with a workflow token: it requires a token
  from an interactive operator session, and every call is logged to a
  separate append-only log. Revocation is an emergency action; the ceremony
  around it belongs to
  [#29](https://github.com/cloudfra/gh-runner/issues/29).

## 7. Release pipeline

`create-release.yaml` splits into a build job and a gated publish job. Inline
shell stays out of the YAML, per `AGENTS.md`.

```yaml
on:
  push:
    tags: ["v*"]
jobs:
  build:
    permissions:
      contents: read
    steps:
      - run: ./scripts/build-release.sh
      - uses: actions/upload-artifact@v7
  publish:
    needs: build
    environment: production
    permissions:
      contents: write
      id-token: write
    steps:
      - uses: actions/download-artifact@v7
      - run: ./scripts/sign-pe.sh
      - run: ./scripts/publish-release.sh
```

Order of operations in `publish`, which matters: build binaries → sign the
PE files and take the signed output back → hash the *final* bytes →
`/v1/manifest` → publish assets and the moving tag. Hashing before PE
signing would put a hash of unsigned bytes in the manifest.

Gate: `environment: production` with required reviewers, at least two
reviewers so one can approve someone else's release, plus a wait timer.
This is what replaces the old "the ceremony authorizes all releases for the
CA's three-year lifetime" reading: the human decision is per release. The
gate also binds every signature request to a specific run through OIDC,
which is what makes the `seq` counter meaningful.

Tag authority, which the earlier design left unaddressed:

- Tag protection rules on `v*` so only the release workflow's actor may
  create them (an owner action; the agent account gets
  `404 Not Found` reading `repos/cloudfra/template-go/tags/protection`).
- The publish job requires `ref_type == tag` **and** that the tag points at
  the commit the build job checked out.
- A tag alone authorizes nothing, because CI status is not an access
  control. The signer trusts the claims above, not a badge.
- The `gha-scale-set-runner/**/private.key` values committed in `gh-runner`
  must be rotated and replaced with secrets before this lane is called
  trusted: those keys control the machines that build the binaries.

Development track, closing the finding that any contributor who can open a
PR to `main` can get a binary onto the dev channel: `environment:
development` on the dev publish job, protection rule restricting it to
`refs/heads/main`, signer requires `ref_type == branch`,
`ref == refs/heads/main`, and `actor` in a configured allowlist. Dev builds
use Development CA leaves, and `--allow-dev` is required on the verifier
command line to accept them.

## 8. Verifier

Ships as a package in template-go plus a `selfupdate` command, consumed by
every app's updater. Verification order — this one differs from the earlier
draft, which executed the downloaded binary before checking hashes:

1. Fetch `manifest.json` and `manifest.sig` for the track.
2. Require `schema == 1`; refuse an unknown schema rather than ignoring it.
3. Verify the signature over the fetched manifest bytes with
   `ecdsa.VerifyASN1` against a leaf that chains to a pinned CA SPKI.
4. Require `published_at` inside the leaf's validity window, and the leaf's
   serial absent from the current CRL.
5. Require `seq` greater than the highest accepted `seq` for
   `(repo, app, track)`.
6. Require `repo` and `app` to match the compiled-in identity, so a valid
   manifest for one app can never authorize another app's files.
7. Download each file; verify SHA-256 and size against the manifest.
8. On Windows, verify Authenticode with `winverify` and require the embedded
   timestamp.
9. Only now run the health check, sandboxed:
   `systemd-run --scope --uid <unprivileged> -p MemoryMax=128M -p TasksMax=64 -p PrivateTmp=yes -p ProtectSystem=strict -p ProtectHome=read-only -p CapabilityBoundingSet= timeout -k 2 5 <path> --version`.
   It is a liveness check, not a trust step, and it never runs with the
   updater's environment.
10. Move into place atomically, then persist the new high-water `seq`.

Deliberate downgrade stays possible: publish a *new* manifest with a higher
`seq` whose files are older builds. That keeps `seq` monotonic instead of
adding an `--allow-rollback` escape hatch.

Bootstrap is trust-on-first-install: the CA SPKI pins are compiled from
`updater/anchors.json` in the source tree, so the out-of-band channel is the
git history of the repository, which is already protected by branch
protection and review. Publishing the same fingerprints in the public
`cloudfra/trust` repo gives a second thing to compare against.

## 9. Revocation, expiry, rotation

- CRLs are built with `x509.CreateRevocationList` and parsed with
  `x509.ParseRevocationList`. One per track, `nextUpdate` 30 days out,
  regenerated weekly by a scheduled workflow that calls `/v1/crl` and
  commits the result. A workflow may commit but must not open a pull
  request — the org blocks Actions-created PRs, and
  [template-go#165](https://github.com/cloudfra/template-go/pull/165)
  removed the workflow that used to.
- Publication path: `cloudfra/trust`, a **new public repository** (owner
  action), at
  `https://raw.githubusercontent.com/cloudfra/trust/main/crl/production.crl.der`
  and `…/crl/development.crl.der`, with anchors beside them.
  [#29](https://github.com/cloudfra/gh-runner/issues/29) records that
  GitHub Pages is not enabled for `gh-runner`, and `gh-runner` is private,
  so Pages on that repo is not a fallback.
- Stale CRL rule: a CRL whose `nextUpdate` passed more than 7 days ago is
  refused; a fetch failure falls back to the cached copy under the same
  rule. This bounds "revoked but not yet visible" at 7 days instead of
  silently accepting forever.
- Leaf expiry does **not** invalidate an old manifest, which is what makes
  short leaves and offline installs compatible. Validity is evaluated at
  `published_at` against the leaf window plus the CRL, anchored on the
  pinned CA. Expiry still fails a signature at the moment of signing.
- CA rotation: new CA issued ≥ 60 days before the old one expires, both
  pins present in `updater/anchors.json` during the overlap, propagated by
  the normal template-go update sweep, and the old pin removed only after
  every consumer released.
- Root ceremony order for
  [#27](https://github.com/cloudfra/gh-runner/issues/27): generate the root,
  record the fingerprint, issue both CAs, test-verify one manifest
  end-to-end, and only then delete every copy of the pre-existing signing
  material. Never run `certtool --yubikey-overwrite` afterwards.
- [#27](https://github.com/cloudfra/gh-runner/issues/27) asks for the
  production CA to live on a YubiKey. That is incompatible with an online
  signer, and `certtool --yubikey` is explicit that "the private key never
  leaves the YubiKey". Resolution: the YubiKey holds the **root**; the
  production CA key is a file the signer uses (Phase 1) and later a second
  YubiKey on the signer's own host (Phase 2, §11). Both CAs stay ≤ 1 year
  so the compromise window is bounded.

## 10. Distribution facts, measured 2026-11-19

The update path must not use the unauthenticated REST API:
`api.github.com/repos/cloudfra/gowebserver/releases/latest` returns
`x-ratelimit-limit: 60` with `cache-control: public, max-age=60`, so 60
requests per hour per IP for the whole fleet. Use release-asset URLs and
moving tags instead:

```console
$ curl -sIL -o /dev/null -w '%{url_effective} %{http_code}\n' \
    https://github.com/cloudfra/gowebserver/releases/latest/download/gowebserver-linux_amd64
https://release-assets.githubusercontent.com/github-production-release-asset/46609806/… 200
```

`releases/latest/download/<asset>` resolves 302 → 302 → 200 with
`cache-control: no-cache` on the GitHub hop and a 5-minute signed SAS URL on
the final hop, so asset URLs cannot be cached indefinitely; the poll target
is `manifest.json` (a few kilobytes), not the binaries. `releases.atom`
returns `max-age=0, private, must-revalidate`, so it is a cheap change
signal but not a cache. Pin the host allowlist for the runner firewall to:
`github.com`, `release-assets.githubusercontent.com`,
`raw.githubusercontent.com`, `token.actions.githubusercontent.com`.

Fleet fixes that this design depends on, all in
`cloudfra/gh-runner`:

- `linux-setup/install-packages.sh` line 2 tells the operator to run
  `curl -fsSL https://gist.githubusercontent.com/jeremyje/…/install-packages.sh | bash -s -- --type runner --token <GITHUB_ACTIONS_TOKEN>`.
  A gist pipe is outside the host allowlist and the script's own
  `DownloadVerified()` helper. Replace the recipe with a release-asset URL
  plus `sha256sums.txt` verification, since that helper already expects a
  "checksum file published in the same release (sha256sums.txt unless
  named)".
- The runner firewall needs its egress allowlist extended to the four hosts
  above, and `actions.githubusercontent.com` plus `objects.githubusercontent.com`
  removed only after checking the artifact path, not before.
- Rotate `gha-scale-set-runner/**/private.key`, move it to a secret, and
  protect the admin lane.

## 12. Verification tooling

Add `scripts/verify-release.sh` to template-go so any release can be audited
by hand and in CI. It is the executable form of §8. The intended output,
which is what the acceptance test in §11 row 5 checks:

```console
$ ./scripts/verify-release.sh cloudfra/gowebserver v3.8.2
manifest.json  schema=1 seq=41 track=production files=5
gowebserver-linux_amd64   sha256 ok  size 74393488
gowebserver-windows_amd64 sha256 ok  size 74659840  authenticode signed 2026-11-19T18:04:11Z
…
OK 5/5 files match manifest signed by leaf 3fa9c2… (CA pin matched, CRL fresh)
$ ./scripts/verify-release.sh cloudfra/gowebserver v3.8.2 --tamper gowebserver-linux_amd64
FAIL gowebserver-linux_amd64 sha256 mismatch manifest=c3d1… actual=9be0…
```

## 13. Owner decisions

1. Create `cloudfra/trust` as a public repository (or name the substitute).
   Revocation has no home until this exists.
2. Confirm the YubiKey split in §9: root on one key, production CA key on
   the signer host in Phase 1, second YubiKey in Phase 2.
3. Name the RFC 3161 TSA used by `osslsigncode -ts`, or accept unsigned
   Authenticode for now.
4. Confirm `environment: production` with at least two required reviewers as
   the per-release gate, and who the reviewers are.
5. Decide whether SmartScreen and notarization reputation are wanted (§2).
   If yes, they are a public-CA purchase and change the leaf policy.
6. Confirm that the `certtool` certificate changes
   ([#27](https://github.com/cloudfra/gh-runner/issues/27)) will come from a
   `certtool` design rather than from flags that do not exist there: as of
   2026-11-19 `cmd/certtool/certtool.go` exposes no CRL, revocation, serial,
   EKU, or timestamp flag, and `--max-path-len` only reaches the CA made by
   `--ca` or `--yubikey-generate-root`.
